## 2. 分模块深挖问答

### 2.1 YOLOv11 检测模块

**Q1：为什么用 YOLOv11 而不是 YOLOv8 / Faster R-CNN / DETR？**
- YOLO 系列是单阶段（one-stage），一次前向出框+分类，比两阶段（R-CNN 系列）在同精度下快一个量级；DETR 端到端但推理慢且需要大量数据微调。
- 具体选 **v11n（nano）**：n 版本参数量约 2.6M、权重 5.6MB，比 s/m/l 小得多，适合跑在 PC CPU 或 Jetson 这类弱算力端，且有 **ONNX 导出通路**。
- v11 相对 v8 的改动点是 C3k2 结构与解耦头 + 更高效的解耦检测头，官方 COCO mAP@0.5 上 n 版本更高（仓库实验报告记录 81.5% vs 78.2%），且参数量更小。
- 但**要说实话**：本项目检测部分大量使用的是**COCO 预训练权重直接推理**，核心创新不在检测精度微调上。

**Q2：为什么用 ONNX Runtime 而不是直接 PyTorch？**
- 推理时不需要 autograd 图和 Python 层 dispatch，CPU 上能省掉大量 Python 开销；并且 ONNX Runtime 可以进一步做 **图优化 / 算子融合**，实测同等模型 CPU 延迟更低。
- 代码里的"自动降级"逻辑是工程上的稳妥做法：

**Q3：20 FPS 是怎么做到的？做了哪些优化？**
按"从贵到便宜"讲：
1. **输入分辨率**：摄像头原始帧统一 resize 到 **宽 320px**（`VIDEO_WIDTH_TARGET=320`），YOLO `imgsz=320`。小目标（远处行人、红绿灯）确实会掉点，但视障场景下更关心近处大目标，权衡后选择速度。
2. **跳帧调度**：`FRAME_SKIP=3`，即每 3 帧才真正跑一次检测，中间帧复用上次结果（`last_detections`）。等价于把检测频率降到 ~7Hz 而视频流仍 20+Hz。
3. **分割降频**：盲道分割比检测更重，**每 3 帧才跑一次**，其余帧复用缓存掩膜 `last_mask`。
4. **ONNX Runtime**：替换 PyTorch 推理后端。
5. **线程解耦**：LLM/OCR/TTS 全部在独立线程，不占用主循环。
6. **异步图传**：Web 图传走 `cv2.imencode` + base64，SocketIO 推送，不阻塞。

**Q4：单目摄像头怎么判断"前方 2 米有行人"？**
- **诚实回答**：严格测距做不到，这里用的是**基于透视投影的面积比代理指标**（CRAM，仓库报告里的 Collision Risk Assessment Model）。原理：同一个物理尺寸的物体，在图像上占的面积与它到相机的距离成反比（近似 ∝ 1/d²）。所以"检测框面积占比"可以作为距离的代理量。
- 补充手段（也是改进方向）：
  - 接入 **ToF/激光测距（VL53L0X）** 补足单目测距，仓库硬件清单已规划；
  - 用**检测框尺寸随时间的增长率**估计接近速度（TTC，Time-To-Collision）——目前是改进方向而非已实现。
- **加分项**：主动承认"面积比不是真实距离"，并说明为什么这在语音播报场景下够用 —— 用户需要的是"快/慢"的粗粒度分级，不是精确米数，而且播报"2 米"反而容易让用户误判。实际播报文案是"警告！前方有汽车，请注意绕行"。

**Q5：红绿灯颜色怎么识别？为什么用 HSV？**
- 不用 RGB 因为光照变化会同时改变 RGB 三个通道的值，很难用固定阈值区分；HSV 里**色相 H 只跟"是什么颜色"有关，与亮度无关**，抗光照鲁棒性更好。
- **关键坑**：OpenCV 的 H 取值范围是 **0~179**（不是 0~359），因为它把 H 压缩成了 uint8。所以红色要拆成两段：`[0,10]` 和 `[160,179]`。

```25:33:E:\盲人辅助系统\src\traffic_light.py

    lower_red1 = np.array([0, 70, 50])
    upper_red1 = np.array([10, 255, 255])
    lower_red2 = np.array([160, 70, 50])
    upper_red2 = np.array([179, 255, 255])
```

- 识别方式：三个掩膜取非零像素数，**投票最多者胜**；少于 10 个像素直接判 `Unknown`（抗噪）。
- **已知缺陷（主动说）**：靠"整框统计"会被反光、路灯、车灯干扰；更稳的做法是按灯位把红绿灯框切成 3 个子区域分别取 H 中位数，或用小分类头单独训练一个红绿灯状态分类器。

### 2.2 盲道分割与循迹

**Q7：为什么用语义分割而不是目标检测？**
- 盲道是**贴地的连续区域**，检测框无法表达"方向"和"延伸趋势"；分割掩膜可以取到**任意区域的质心**，天然适合做循迹。

**Q8：为什么质心取"图像下三分之一"？**
- 透视关系：地面在画面里越靠下越近用户的脚。盲道在画面**上部**的像素其实是**远处**的盲道，下部才是脚边的。取下部区域质心 = 取"用户当前脚下盲道的横向位置"，这才是决定"该往哪迈"的量。
- 角度上：地面在图像下缘的等效俯仰角约 45°，接近人眼低头扫视盲道时的主视觉区。

**Q9：整个循迹算法怎么走的？**
1. 分割模型输出掩膜 → 取**面积最大**的连通域作为盲道掩膜（`best_mask`）。
2. 图像**纵向三分**：上 1/3 = 远处，中 1/3 = 中景，下 1/3 = 近处（脚下）。
3. 在下 1/3 求质心 `cX_bottom`（若无则退化到中 1/3）。
4. **平移模式（Shift）**：`|cX_bottom - centerX| > 16.5% 宽度` → 偏左播"向左平移"，偏右播"向右平移"。
5. **转向模式（Align）**：已在安全区时，取上 1/3 质心 `cX_top`，`|cX_top - cX_bottom| > 15% 宽度` → 播"向左微调/向右微调"，否则"直行"。
6. **优先级**：障碍物判断在盲道循迹**之前**，有障碍先报障碍（安全优先）。

**Q10：阈值（16.5% / 15%）是怎么定的？**
- 经验值 + 实测调参：太小会左右横跳、语音反复播报"向左平移/向右平移"（用户会晕），太大则该纠偏时不纠偏。16.5% ≈ 画面宽度的 1/3 容差带。**改进方向**：做成自适应阈值（按最近 N 帧的偏差趋势做迟滞判断），或直接用 PID 思路做连续纠偏而不是离散三档。

**Q11：盲道分割模型哪来的？**
- 仓库配置 `SEG_MODEL_PATH = "models/blind_path.pt"`，实际是**在公开数据集/自采数据上微调 YOLO-seg** 得到的权重。面试时要说清：预训练 COCO 权重 → 标注盲道/斑马线数据 → 微调；数据量、标注工具、训练超参要提前背下来。**这是最容易翻车的追问点。**

**Q12：为什么分割每 3 帧才跑一次？**
- 分割比检测重 2~3 倍，而盲道位置在 1/3 秒内几乎不变。用"时间上的低通滤波"换算力，掩膜缓存复用。

### 2.3 Qwen-VL 多模态大模型

**Q13：Qwen-VL 在这个系统里到底解决了什么问题？**
- 检测模型输出的是**离散标签**（"人""车"），视障用户真正需要的是**关系与语义**："对面是绿灯，斑马线上没有人，可以过"、"这条盲道被共享单车截断了"、"药盒上写着每日两次，饭后服用"。
- 这些都超出 80 类 COCO 的表达能力，属于**开放世界理解**，正是 VLM 的强项。

**Q14：为什么要异步线程 + 回调？**
- VLM 端到端延迟 **2~3 秒**。如果同步调用，主视频循环会被卡住，避障功能随之失效（这是**安全性问题**，不只是体验问题）。
- 实现：`analyze_scene_async` 起 daemon 线程 → 结果通过 `callback_func` 回主线程 → 主线程只负责入 TTS 队列。

```53:66:E:\盲人辅助系统\src\llm_agent.py
    def analyze_scene_async(self, frame, callback_func, query=None):
        """
        异步分析场景
        frame: cv2 图像
        callback_func: 回调函数，接受 (text_result)
        query: Optional user question (str)
        """
        if self._is_thinking or not self.client:
            return

        self._is_thinking = True
        
        # Start a thread
        thread = threading.Thread(target=self._worker, args=(frame, callback_func, query))
```

- 还有一个细节：`_is_thinking` 标志位做**并发去重**，避免用户连按 `D` 触发多个请求堆在云端。

**Q15：提示词怎么设计的？**
- 三个约束：**角色**（视障助手）、**内容重点**（路况/障碍/文字/危险）、**长度限制**（≤25 字、口语化）。

- **提示工程经验**：字数约束对 TTS 场景极其重要 —— 25 字大约 4~6 秒播报时长，超过就会占用视障用户的行走注意力窗口；而且字数太长时用户听不清关键词。
- **可讲的坑**：VLM 有时会**幻觉**（说出画面里没有的路牌文字）。缓解手段：提示词里明确"只描述能确认看到的内容，不确定就说看不清"；进一步可以对 OCR 结果做交叉验证。

**Q16：为什么用 OpenAI 兼容接口 + SiliconFlow，而不是本地部署 Qwen-VL？**
- 本地跑 8B 视觉模型需要 ≥16GB 显存（量化后 4bit 约 6GB），远超项目目标终端（Jetson Orin Nano 8GB 勉强能跑但帧率极低）；SiliconFlow 提供 **OpenAI 兼容 API**，代码里只需要换 `base_url` 和 `model` 就能切到自建 vLLM / Ollama，**可迁移性好**。
- 配合"快慢系统"架构：网络不好时自动降级为纯本地检测 + OCR 功能，系统不瘫。

**Q17：图片怎么传给模型？**
- `cv2.imencode('.jpg', frame)` → base64 → `data:image/jpeg;base64,...` 塞进 `image_url`。用 JPEG 而非 PNG 是为了压缩体积（上传流量与编码耗时）。
- 注意模型对**极低分辨率图像**识别会退化（320px 宽对读路牌文字偏糊），所以 OCR 与 VLM 的输入应该用**更高分辨率的原始帧**——这是当前实现的一个已知短板，也是一个很好的改进点。

**Q18：视觉问答支持哪些形式？**
- 按 `D` 键 = 无 query 的场景描述；语音指令走 `CHAT` 意图时会把**用户原话**作为 query 传入，走同一条 VLM 通路。所以"前面的店名叫什么"这类问题，会连同当前帧一起发给 VLM。

**Q20：为什么按需触发而不是常驻实时 OCR？**
- OCR 是最重的模块之一，常驻会直接把 FPS 打到个位数。按 `T` 触发是"用户需要读字才花这个算力"，符合视障交互里**需求驱动**的交互范式。
- 另外 OCR 运行在独立线程 + 期间 5 秒内屏蔽避障告警（`ocr_speaking_until`），避免两路语音打架。

- 过滤策略：**关键词黑名单 + 纯数字剔除 + 空串剔除**。

### 2.5 TTS 语音调度

**Q22：为什么自己写优先级队列，而不是直接调 TTS 播？**
- 直接播会有三个问题：**排队消息无法抢占**（危险警报排在后面等着）、**消息堆积**（网络抖动时积压几十条，播报落后于现实几秒）、**并发调用冲突**（多个线程同时播会串音）。
- `PriorityQueue` + 单 worker 线程 + P0 清空队列，是最贴近"打断式语音交互"的标准解法。

**Q64:（顺序修正）Q22 回答要点**：
- **P0（危险）**：`clear_queue()` + `pygame.mixer.music.stop()` 立即打断当前播报；
- **P1（信息）**：排队等待。
- **is_busy()** 同时检查"队列非空 / 正在处理 / mixer 正在播"三个状态。

```69:81:E:\盲人辅助系统\src\tts_engine.py
    def speak(self, text, priority=1):
        """
        Add text to the speech queue.
        """
        if not text:
            return
            
        # For Priority 0 (Warning), we interrupt everything
        if priority == 0:
            self.clear_queue()
            # If it's a warning, we might want to stop current playback immediately too?
            # For now, just clearing queue and letting current sentence finish usually feels more natural,
            # but for DANGER, we might want stop().
            # Let's stop playback for Priority 0 to be instant.
            if pygame.mixer.get_init():
                pygame.mixer.music.stop()
            
            self.queue.put((priority, text))
```

**Q23：TTS 用什么引擎？为什么？**
- **Edge-TTS**：微软 Azure 神经语音的免费客户端，**无需 API Key**、音质自然（`zh-CN-YunxiNeural` 青年男声）、延迟低。牺牲是**依赖网络**——所以做了 MD5 缓存（见 Q24）来降低首次之外的延迟。
- 语速 `+35%`：视障用户行走时语速过慢会拖慢节奏，过快则辨识困难，+35% 是实测平衡点。
- **竞品对比**：pyttsx3 本地离线但音质机械；Coqui TTS 可离线但中文模型重、推理慢；Azure 正式商用要付费。

**Q24：MD5 文本哈希缓存解决了什么？**
- 播报文案是**高度重复**的："警告！前方有汽车，请注意绕行" 一天要播几十次。每次都请求网络 TTS 是浪费且延迟叠加。
- key = `md5(text)` → 文件名 `tts_{hash}.mp3`；命中直接播放本地文件，**零网络延迟**。
- **缓存收益**：命中时播报延迟从 ~500ms 降到本地播放的几十 ms；也降低了对外 API 的调用量。
- **可讲的坑**：`md5` 在这里不是安全用途，仅作哈希键；缓存文件会无限增长（可改进：LRU 清理 + 容量上限 + 定期清理旧文件）。
- **改进方向**：预生成常用提示词音频（"向左平移""直行"等）打包进安装目录，首次运行即可离线。

### 2.6 双尺度导航（GIS + 视觉）

**Q25：为什么地图导航和视觉避障要分宏观/微观两层？**
- **宏观（GIS）** 解决"从A到B走哪条街"，是**全局最优路径问题**；但它不关心"前方 5 米有个没被地图收录的共享单车"。
- **微观（视觉）** 解决"脚下这一步怎么走"，是**局部实时避障问题**；但它没有全局视野，会迷路。
- 两者信息互补、时延量级不同（地图指令几十秒一次，视觉指令毫秒级），所以必须分层，并且用**优先级仲裁**合并。

**Q26：折线投影吸附（map-matching）是什么？为什么需要它？**
- 手机 GPS 有 5~15 米误差，直接拿原始坐标算"离转弯点多远"会跳变（可能算出 8 米也可能算出 30 米）。
- 做法：把高德返回的 `polyline`（折线）作为"道路中心线"，把 GPS 点**投影到折线的每一段上**，取距离最小的投影点。

```480:487:E:\盲人辅助系统\src\map_agent.py
        # Projection parameter t
        t = ((px - x1) * dx + (py - y1) * dy) / (dx * dx + dy * dy)
        t = max(0, min(1)) # Restrict to within the segment
        
        proj_x = x1 + t * dx
        proj_y = y1 + t * dy
```

- **`t` 限制在 [0,1] 的原因**：点在线段延长线上时，数学上的正交投影会落到线段外，导致吸附到"不存在的路"。夹紧到 [0,1] 后，投影点必然在线段上，退化时吸附到端点。
- 距离用 **Haversine 公式**算球面距离（而不是欧氏），因为经纬度是球面坐标。

**Q27：偏航检测与重规划？**
- `min_dist > 60m` → 判定严重偏航 → 调 `get_custom_route` 用**当前位置作为新起点**重新规划，并播报"您已偏航，正在为您重新规划路线"。
- `8m < min_dist <= 60m` → 轻微偏航 → 只给**微观纠正**："请向 2 点钟方向，走约 N 步即可回到主路线"，其中 `N = min_dist / 0.6`（步长）。
- 冷却时间：偏航纠正 15s 冷却，直行巡航提示 45s 冷却，避免刷屏。

**Q28：为什么播报用"时钟方位"而不是"向左/向右转"？**
- 视障用户在路口往往**不知道自己的面朝方向**，传统导航说"左转"需要用户建立"我的左边 = 地图的左边"的映射，认知负担大且容易出错。
- 做法：算**真北方位角 bearing**（0~360°，正北=0）→ 减去用户**当前朝向 heading**（来自 IMU）得到**相对角**（-180~180）→ 映射到 12 个扇区 → 播"向您的 2 点钟方向"。

```519:531:E:\盲人辅助系统\src\map_agent.py
    def _get_clock_direction(self, bearing, current_heading):
        """
        Combine target bearing (0-360) and current user heading (0-360) into clock direction.
        :param bearing: target point's true north bearing (0-360)
        :param current_heading: user's current face heading (0-360)
        :return: 1-12 clock number
        """
        # Calculate relative angle (-180 to 180)
        relative_angle = (bearing - current_heading + 360) % 360
        if relative_angle > 180:
            relative_angle -= 360
            
        # Map to 12 clock sectors (each 30 degrees)
        clock_value = round(relative_angle / 30.0)
```

- **加分项**：这个设计是**视障人机交互设计**（HCI）领域有依据的设计原则——用**相对身体坐标系**代替环境坐标系，是视障导航的标准做法。

**Q28b：为什么地图指令里的"向东步行100米"要清洗成"正前方步行100米"？**
- 同理，"东"是环境坐标系，需要用户心算罗盘。清洗成"正前方"后，配合时钟方位，用户只需做**身体旋转**这一个动作。

**Q29：公交/地铁换乘怎么播报？**
- 高德 `direction/transit/integrated` 返回的是**分段结构**（walking / bus / subway 混排）。代码把每段的 walking steps 和 buslines **展平成一维步骤列表**（`nav_steps`），公交段生成"在 XX 站乘坐 XX 路，经过 N 站在 XX 站下车"。
- 失败降级：公交接口失败（城市码不对、距离过远）→ **自动回退到步行路径**。

### 2.7 GPS-PDR 融合定位

**Q30：为什么不用纯 GPS？**
- 纯 GPS 有三个硬伤：**更新频率低**（1Hz 甚至更低）、**城市峡谷效应**（高楼/桥下多路径反射，位置漂几十米）、**短时精度抖动**。对"我还有几步到路口"这种需求，GPS 根本不够细。

**Q31：PDR（Pedestrian Dead Reckoning）原理？**
- 人行走的步频在 2 Hz 左右（1.8~2.2 步/秒），IMU 可检测**周期性冲击峰值**识别"迈了一步"。
- 每步沿**当前朝向 heading** 前进一个步长 `step_length`（默认 0.6m，由个人身高/步幅决定，可用 IMU 动态标定）。
- 转米为经纬度：纬度 1° ≈ 111132 m；经度 1° 的距离随纬度收缩，需乘 `cos(lat)`。

```44:56:E:\盲人辅助系统\src\sensor_fusion.py
        # Decompose distance into lon/lat offsets based on heading
        # North latitude (dy)
        dy = self.step_length * math.cos(math.radians(self.heading))
        # East longitude (dx)
        dx = self.step_length * math.sin(math.radians(self.heading))
        
        # Convert offset (meters) to lat/lon degrees
        # 1 degree latitude is about 111132 meters
        delta_lat = dy / 111132.0
        
        # 1 degree longitude distance varies with latitude, approximately 111132 * cos(lat)
        delta_lon = dx / (111132.0 * math.cos(math.radians(self.current_lat)))
```

**Q32：为什么必须用 GPS 做锚点？**
- PDR 的误差是**累积的**：步长估计误差 5% 走 100 米就偏 5 米；IMU 的航向漂移（yaw drift）是单轴积分误差，尤其在没有磁力计校准时，几分钟就能偏几十度。
- 所以架构是 **GPS 定期给绝对锚点，PDR 在锚点之间做高频推算** —— 这就是典型的"零速修正 ZUPT 之外的低成本组合导航"思路。

**Q33：GPS 滤波怎么做的？三层？**
1. **精度门槛**：手机上报 `accuracy > 5000m` 直接丢弃。
2. **跳点检测**：相邻两点算速度（`dist/dt × 3.6`），**> 150 km/h** 判为 GPS 跳变丢弃；超过 60 秒无更新视为新会话直接放行。
3. **精度加权滑动窗口**：保留最近 3 个点，权重 = `时间权重(i+1) × 精度权重(100/(acc+5))`。精度数字越小（越准）权重越大。

```166:180:E:\盲人辅助系统\web\app.py
    if len(gps_history) >= 2:
        total_w = 0
        avg_lat = 0
        avg_lon = 0
        for i, (hlat, hlon, hacc) in enumerate(gps_history):
            # Time weight (current=3, previous=2, earlier=1)
            time_w = i + 1 
            # Accuracy weight (inverse: smaller accuracy value means more accurate, so higher weight)
            # Use 1 / (acc + 1) as weight
            acc_w = 100.0 / (hacc + 5.0) 
            
            w = time_w * acc_w
            avg_lat += hlat * w
            avg_lon += hlon * w
            total_w += w
```

- **为什么纯时间加权不够**：如果最近一个点精度极差（acc=200m）而前一个很准（acc=3m），纯时间加权会让差点的权重更大，结果更抖。精度加权正好解决这个。
- **注意**：项目里设置了 `accuracy > 5000m` 的宽松门槛，是**为了支持室内演示**；真实产品应收紧到 30~50m。

**Q33b：Qwen-VL 用了什么模型、走什么接口？**
- 模型：`Qwen/Qwen3-VL-8B-Instruct`（SiliconFlow）；ASR：`FunAudioLLM/SenseVoiceSmall`。
- 统一走 **OpenAI 兼容 SDK**（`from openai import OpenAI` + `base_url`），好处是切换供应商只改两行配置。

### 2.8 远程监护平台

**Q34：Web 端为什么用 SocketIO 而不是裸 WebSocket / MJPEG？**
- **SocketIO** 的优势：自带**重连机制**（手机锁屏、切换网络后自动恢复）、**房间/广播**、**降级为长轮询**、事件语义化（`video_frame`、`voice_msg`、`update_gps`）比手写报文清晰。
- 视频图传用 base64 JPEG 走 SocketIO 的原因：能**复用同一条连接**，省掉额外端口与鉴权；代价是体积比裸 MJPEG 大（base64 膨胀 ~33%）。生产环境会考虑 WebRTC 或 H.264。
- MJPEG `<video>` 路由保留作为兼容/降级方案。

**Q35：SocketIO 为什么用 `async_mode='threading'`？**
- 因为项目同时用了 `pygame`（音频播放）、`asyncio`（edge-tts）、`SpeechRecognition`，这些与 eventlet 的 green thread 协作不好（eventlet 会 monkey-patch，且与 asyncio 循环冲突）。`threading` 模式最稳，代价是并发规模不如 eventlet —— 但本场景是单用户低并发，完全够。

**Q36：为什么 HTTPS 自签证书？**

- 用 `ssl_context='adhoc'`（pyOpenSSL 自签），手机上需手动信任证书。生产环境应换成正规证书。

### 2.10 性能与工程化

**Q41：整体延迟链？**
- 视频帧处理 < 50ms；TTS 本地缓存播放 ~50ms；网络 TTS 生成 ~500ms；VLM 端到端 2~3s（异步，不阻塞）；OCR ~0.3~1s（异步，按需）。
- 播报总链路：按键 → 采集 → 推理 → 入队 → 播放，在本地缓存命中情况下 **< 300ms**。

**Q42：线程模型？**
- 主线程：视频采集 + 检测 + 决策 + 渲染。
- TTS worker 线程：单消费者 + 优先级队列。
- LLM 线程：每次请求一个 daemon 线程（靠 `_is_thinking` 去重）。
- OCR 线程：按需起线程。
- SocketIO 线程：Web 服务独立线程。
- 通信：主要通过 `threading` 共享状态 + `global_stats` 字典 + `lock` 保护 `outputFrame`。

**Q43：为什么不用 asyncio 全异步？**
- 因为**依赖栈是同步的**（pygame、SpeechRecognition、ultralytics 推理），强行 async 化收益低、坑多。多线程 + 队列是更务实的选择。**可作为"如果重写会怎么做"的改进回答**：用 asyncio 做统一调度，或把检测循环放独立进程用 multiprocessing 共享内存。

**Q44：单目相机测距的未来方案？**
- **ToF 激光测距（VL53L0X）**：仓库硬件清单已规划，能测 2m 内悬空障碍（手杖的盲区）。
- **双目/深度相机**：RealSense，但功耗与成本高。
- **单目 + 已知物体尺寸的先验**：人宽约 0.5m、井盖直径 0.7m、公交车高 3m → 反推距离（比面积比更准，但要维护尺寸表）。
- **用框增长率估 TTC**：`d(t) ∝ 1/sqrt(area)`，两帧间可估接近速度。

### 2.11 商业与产品思考

**Q45：这个产品的真实用户痛点是什么？**
- 视障人士出行最怕的不是"不知道有什么"，而是**来不及反应**（突然窜出的电动车、静音外卖车）。
- 导盲杖的缺陷是**只能感知地面、腰以下**；本系统补的是**上方视野**（路牌、树枝、悬挂物）和**语义**（这是什么、能不能走）。
- 使用者画像：**老年视障 + 独居**是最高价值人群，远程监护的"亲情连接"是真正的购买理由（子女买，不是本人买）。

**Q46：和 OrCam 这类商业产品比，优势/劣势？**

- 劣势：OrCam 的**阅读体验与工业设计**远强于本项目；本项目本质是**开源原型**，没有经过真实视障用户的长期可用性测试。

- **跌倒检测**与紧急播报闭环。
- **可穿戴形态**（眼镜/胸挂）+ 骨传导 + 触觉编码，替代纯语音。

### 2.12 常见"为什么/权衡"汇总（速查表）

| 问题 | 一句话回答 |
| --- | --- |
| 为什么不用纯语音？ | 语音在嘈杂街道不可靠，必须有按键兜底；且视障用户操作按键比触屏快 |
| 为什么按 T 才 OCR？ | OCR 最重，常驻会把 FPS 打到个位数；按需触发符合"需求驱动" |
| 为什么本地模型不用最大号？ | 端侧算力/功耗约束，且避障任务不需要长尾识别精度 |
| 为什么云端大模型不用更小的？ | 场景描述与问答需要常识与推理，7B 以下 VLM 幻觉明显增多 |
| 为什么 TTS 要打断？ | 危险警报延迟 3 秒就失去意义，必须抢占式播报 |
| 为什么不用地图 SDK 的语音导航？ | 商业 SDK 播报是给开车人设计的（"向东300米"），对视障用户不可用，需自研语义改写 |
| 为什么 GPS 要滤波？ | 手机 GPS 在城市峡谷误差可达 15m+，直接用会导致频繁误报偏航 |
| 为什么 PDR 步长写死 0.6m？ | 简化实现；真实做法是开机标定或按 IMU 加速度积分自适应 |
| 为什么分割每 3 帧？ | 分割是检测的 2~3 倍开销，而盲道位置秒级不变 |
| 为什么栈里没有深度学习框架训练代码？ | 检测/分割权重来自预训练+微调，项目重心在系统集成与工程落地 |
| 为什么不用 Kafka/Redis？ | 单用户场景，Flask 内存态 + SQLite 完全够，避免过度设计 |
